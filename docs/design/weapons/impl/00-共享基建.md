## 1. 叠层 Buff API（Weapon 级 / Ship 级）

### 1.1 动机与与既有框架的关系

- 首批两处叠层（**电荷针刺淤积**：按秒连续衰减 + 安全闸 clamp；**穷距持续演算**：命中窗口衰减 + 目标身份绑定）均**不匹配** `StackingShipBuffs` 的「到期一次性清零」语义（电荷针刺是 -10 层/s 连续流失，穷距是 3s 未命中后按速率流失），故不复用、不改造既有框架，另立接口化 API。
- 既有 `StackingShipBuffs`（标记/潮汐类时长 Buff）保持不动，继续服务其现有调用方；新 API 与其共存，各自语义清晰。
- 新 API 不分正负中性（用户铁律），只提供统一承载、生命周期与查询入口；「正/负」语义由 `maintainStatusForPlayerShip` 的 negative 参数在具体武器处表达。

### 1.2 状态载体（唯一确定方案，已核实）

- **Ship 级**：`ship.customData["astd_buff:ship:<buffId>"]`。
- **Weapon 级**：`WeaponAPI` 无 customData（§0 已核实），状态挂**舰船侧复合键**：
  `ship.customData["astd_buff:weapon:<buffId>:<slotId>"]`，`slotId = weapon.slot.id`（`com.fs.starfarer.api.loading.WeaponSlotAPI.getId()`，已核实存在）。
  - 键级联在 ship 上的好处：船变 hulk / 移除时状态随实体生命周期自然终结，无需跨表清理；同一艘船两件同型武器天然隔离。
  - 复合键由 BuffHost 实现内部生成，调用侧不感知拼接规则。
- 引擎级插件注册表沿用现有模式：`engine.customData` 存插件引用（`StackingShipBuffs.ensurePlugin` 同款）。

### 1.3 接口族设计

落文件路径（新增包，不与既有 `combat/buffs/` 冲突）：

| 文件 | 内容 |
|---|---|
| `src/main/kotlin/cn/kasuminova/astd/api/buff/Buff.kt` | `Buff` 接口 + `BuffLifetime` 枚举 |
| `src/main/kotlin/cn/kasuminova/astd/api/buff/StackableBuff.kt` | `StackableBuff : Buff` 接口 + `StackDecayMode` 枚举 |
| `src/main/kotlin/cn/kasuminova/astd/api/buff/BuffHost.kt` | `BuffHost` 接口（承载/查询入口） |
| `src/main/kotlin/cn/kasuminova/astd/api/buff/BuffAccess.kt` | `ShipAPI` 顶层扩展函数族（便捷入口） |
| `src/main/kotlin/cn/kasuminova/astd/impl/buff/BuffHostImpl.kt` | `BuffHostImpl`（customData 读写 + 复合键生成） |
| `src/main/kotlin/cn/kasuminova/astd/impl/buff/BuffTickPlugin.kt` | 引擎级每帧心跳（`BaseEveryFrameCombatPlugin`） |

**`Buff`**（基础单位，注释必须含：类简介「舰船/武器级战斗状态的最小承载单位」、动机「统一首批叠层机制的存取与生命周期语义」、每个成员作用）：

```kotlin
interface Buff {
    /** 全局唯一 id：同时充当 customData 键段与 stat modifierId 前缀，须以 `astd_` 开头。 */
    val id: String

    /** 生命周期策略：决定 BuffTickPlugin 何时回收。 */
    val lifetime: BuffLifetime

    /** 宿主状态是否仍有效（宿主死亡/引用失效时返回 false，插件据此回收）。实现必须轻量、无副作用。 */
    fun isHostValid(): Boolean

    /**
     * 每帧心跳钩子。amount 为经时间膨胀修正前的真实秒数；
     * 叠层衰减、状态表刷新在此发生。默认空实现（非 StackableBuff 的纯标记可不动）。
     */
    fun advance(amount: Float) {}

    /** 回收钩子：插件移除本 Buff 前调用一次，用于 unapply stat 修改。默认空实现。 */
    fun onRemove() {}
}

enum class BuffLifetime {
    /** 随宿主实体存在（hulk/移除即回收）。电荷针刺淤积、穷距叠层用此档。 */
    HOST_BOUND,
    /** 自管理生命周期：advance 内自行判定终结并调用 BuffHost.remove。湮灭涡旋吞噬池类状态用此档。 */
    SELF_MANAGED,
}
```

**`StackableBuff : Buff`**（可组合叠层语义，注释含：类简介「带整数层数的 Buff」、动机「电荷针刺/穷距及后续叠层机制的统一读写面」、每个成员作用）：

```kotlin
interface StackableBuff : Buff {
    /** 当前层数，[0, maxStacks]。 */
    val stacks: Int

    /** 层数上限（可被难度缩放/安全闸动态调整，如电荷针刺耗散 50% 闸 clamp 后的实际允许上限）。 */
    val maxStacks: Int

    /**
     * 叠加 [n] 层并返回实际生效层数变化（受上限 clamp）。
     * n 可为负（强制扣层），实现内部统一走同一 clamp 路径。
     */
    fun addStacks(n: Int): Int

    /** 衰减模式：决定 advance 的默认语义。 */
    val decayMode: StackDecayMode
}

enum class StackDecayMode {
    /** 连续流失：stacksPerSecond 速率按秒连续扣减（电荷针刺 -10/s）。 */
    CONTINUOUS,
    /** 窗口后流失：最近刷新起静默 windowSeconds 后按 stacksPerSecond 扣减（穷距 3s 窗口）。 */
    WINDOWED,
    /** 到期清零：durationSeconds 后整 Buff 移除（对齐 StackingShipBuffs 语义，供后续迁移用）。 */
    EXPIRE_ALL,
}
```

**`BuffHost`**（承载者查询面，注释含：类简介「一艘船的全部 Buff 登记表」、动机「隔离 customData 键拼接细节」、每个成员作用）：

```kotlin
interface BuffHost {
    /** 按 id 查 Ship 级 Buff；不存在返回 null。 */
    fun find(id: String): Buff?

    /** 按 id 查指定武器的 Weapon 级 Buff；不存在返回 null。 */
    fun findByWeapon(id: String, weapon: WeaponAPI): Buff?

    /** 注册一个 Buff（同键已存在时记录 WARN 并覆盖——属程序错误，不静默）。 */
    fun register(buff: Buff, weapon: WeaponAPI? = null)

    /** 立即移除并触发 onRemove。 */
    fun remove(buff: Buff, weapon: WeaponAPI? = null)

    /** 供 BuffTickPlugin 每帧遍历的内部视图；调用侧不得修改。 */
    fun all(): List<Pair<Buff, WeaponAPI?>>
}
```

**便捷入口**（`BuffAccess.kt`，顶层扩展函数，形态对齐设计案要求并修正为真实可行载体）：

```kotlin
/** 取该船的 BuffHost；首次访问时在 ship.customData 惰性创建并登记心跳插件。 */
fun ShipAPI.buffHost(): BuffHost

fun ShipAPI.getBuff(id: String): Buff?

fun ShipAPI.getOrCreateBuff(id: String, creator: () -> Buff): Buff

/** Weapon 级：内部走复合键（WeaponAPI 无 customData，已核实 jar）。 */
fun ShipAPI.getBuffByWeapon(id: String, weapon: WeaponAPI): Buff?

fun ShipAPI.getOrCreateBuffByWeapon(id: String, weapon: WeaponAPI, creator: () -> Buff): Buff
```

- 设计案示例 `fun ShipAPI.getChargeNiddleBuff(): ChargeNiddleBuff?` 这类**具体武器强类型入口不沉淀进公共 API**（避免公共包反向依赖武器包）；各武器在自己包内写一行扩展 `fun ShipAPI.chargeNeedleBuff() = getBuff("astd_charge_needle_stacks") as? ChargeNeedleStacks`。
- 心跳插件 `BuffTickPlugin`：首次 `buffHost()` 时 `engine.addPlugin` 注册（`engine.customData` 键 `astd_buff_tick_plugin` 去重），每帧遍历 `engine.ships` 上登记过的 BuffHost，对 `lifetime == HOST_BOUND` 且 `!isHostValid()` 的回收；`advance(amount)` 透传。暂停（`engine.isPaused`）直接跳过。
- 玩家可见表现：Buff 本身不渲染；由具体武器在 `advance` 内调用 `maintainStatusForPlayerShip`（层数/倍率）与浮字/粒子（§4.2）。接口 javadoc 中写明「特殊数值必须配玩家可见表现（HUD/特效/浮字），禁止有机制无反馈」。

### 1.4 单元测试清单（`src/test/kotlin/cn/kasuminova/astd/impl/buff/`）

1. 复合键生成：同 buffId 不同 slotId 互不覆盖；Weapon 级键不含 ship 引用泄漏（换船后查不到）。
2. `getOrCreateBuff` 幂等：两次调用返回同一实例，creator 只执行一次。
3. `addStacks` clamp：加上限/扣到 0/负输入；返回值=实际增量。
4. `register` 同键覆盖时输出 WARN（捕获 logger 断言）。
5. CONTINUOUS/WINDOWED/EXPIRE_ALL 三种衰减的参考实现（以测试桩 Buff 驱动 `advance`）：速率、窗口边界（恰 3s / 3s+ε）、到期清零各自正确。
6. 心跳回收：`isHostValid()=false` 后下一 tick 移除且 `onRemove` 恰好调用一次。
7. 0 值防线：`stacksPerSecond = 0`、`maxStacks = 0` 输入时行为明确（clamp 到下限并记 WARN，不静默恒零/除零）。

## 2. 锥状冲击结算组件（ConeImpactHandler）

### 2.1 职责边界

纯结算 + 一次性几何筛选：输入一次引爆/命中事件，输出「范围内目标清单 + 逐目标伤害结算」。**不含**每帧近炸检测循环（那是调用方的弹体脚本职责）、不含 VFX 树构建（只发一个回调让调用方画）。

### 2.2 输入与流程

落文件路径：

| 文件 | 内容 |
|---|---|
| `src/main/kotlin/cn/kasuminova/astd/api/combat/ConeImpact.kt` | `ConeImpactSpec` 数据类 + `ConeTargetFilter` 接口 |
| `src/main/kotlin/cn/kasuminova/astd/impl/combat/ConeImpactHandler.kt` | `ConeImpactHandler`（object 无状态结算器） |

```kotlin
/** 锥状冲击的一次性结算声明（注释逐项写明作用与单位）。 */
data class ConeImpactSpec(
    val origin: Vector2f,          // 锥顶点（命中点/引爆点）
    val direction: Vector2f,       // 锥中轴单位矢量（命中矢量/飞行矢量；调用方保证归一化）
    val halfAngleDeg: Float,       // 锥半角（面板锥角/2，由难度锚点换算后传入）
    val range: Float,              // 锥长（su）
    val damage: Float,             // 面板倍率折算后的基准伤害
    val damageType: DamageType,    // 正电子 FRAGMENTATION；贯星 FRAGMENTATION + 同锚点 ENERGY(EMP) 两发
    val empDamage: Float = 0f,     // 附带 EMP 伤害（贯星），0 表示无
    val source: ShipAPI?,          // 伤害来源（归功/AI 仇恨）
    val owner: Int,                // 归属方（敌我过滤基准）
    val filter: ConeTargetFilter,  // 目标过滤策略
    val hitShips: Boolean = true, val hitFighters: Boolean = true, val hitMissiles: Boolean = true,
)

fun interface ConeTargetFilter {
    /** 粗筛后逐目标终判；返回 true 纳入结算。 */
    fun accept(target: CombatEntityAPI): Boolean
}
```

结算流程（`ConeImpactHandler.resolve(engine, spec): List<CombatEntityAPI>`）：

1. **粗筛（性能关键）**：`CombatUtils.getEntitiesWithinRange(spec.origin, spec.range)` 一次圆形范围查询（LazyLib 走空间网格，已在 GCP 路径验证）。破晓档 600su/80° 下候选量从全图（数百实体）压到半径内（通常 <30）。
2. **类型与归属筛**：按 `hitShips/hitFighters/hitMissiles` 与 `owner` 剔除；`isHulk` 剔除；顶点处直接命中体是否豁免由 filter 决定（贯星命中目标自身不重复吃锥面伤害）。
3. **角度精筛**：`target.location` 与 origin 的矢量点积算夹角 ≤ halfAngleDeg；目标碰撞半径并入判定（`atan(radius/dist)` 放宽，避免擦边大目标漏判）。0 值防线：`dist ≈ 0`（顶点重叠）直接纳入，不除零。
4. **结算**：逐目标 `engine.applyDamage(target, point, damage, damageType, empDamage, ...)`；一次性调用，无二次 onHit 回环风险（applyDamage 不触发 onHitEffect）。
5. **VFX 回调**：结算器返回命中清单后由调用方触发各自 VFX（正电子：缩小版蓝色锥面闪光；贯星：大光柱 + 锥状冲击特效；摧锋：后续接入）。锥面视觉原型统一收敛为「顶点闪光 + 沿中轴扩散的冲击锥 sprite/粒子」，三案共用 RenderEntity 组件、参数化锥角/长度/调色。

### 2.3 三案差异

| 案 | 触发位置 | 每帧成本 | filter | 备注 |
|---|---|---|---|---|
| 正电子冲击波 | 弹体 EveryFrame 脚本自爆/近炸引爆时调用一次 | 每帧近炸检测是**检测侧**成本：每发弹体每帧 `getEntitiesWithinRange(proj.loc, 近炸距离)` 粗筛 + filter 只收导弹/战机；1.5s 间隔下在场弹体 ≤2，可控 | 导弹/战机触发引爆；结算时 hitShips=true（自爆波及）但引爆判定 filter 严格排除舰船 | 首次落地组件；`collisionRadius=0` 无 onHit 路径 |
| 贯星之矛 | `OnHitEffect` 内调用一次 | 无每帧成本（射速 7s/发） | 舰船+战机+导弹；命中本体豁免 | 锥长/锥角直接吃难度三锚点；破晓 600su/80° 由粗筛兜底 |
| 摧锋（后续） | k≥3 解锁后 OnHit 调用 | 无每帧成本 | 同贯星族 | 本组件预留，不在首批范围实现 |

### 2.4 单元测试清单

1. 几何：锥内/锥外/恰在半角边界/恰在锥长边界的目标取舍；顶点重叠（dist=0）纳入。
2. 大目标擦边：碰撞半径放宽修正生效。
3. 归属与类型过滤矩阵（敌/我、舰/机/弹 9 宫格）。
4. 粗筛结果与全表扫结果一致性（随机布点 1000 次对照——保证网格查询不换语义）。
5. `direction` 非单位矢量输入时记录 WARN 并归一化（不静默产出错误锥形）。

## 3. 并行 worktree 合并协议

十组武器并行实装会共同触碰以下共享文件。约定核心：**键名空间隔离 + 固定追加位置 + 排序规则 + 单人收口**。

| 共享文件 | 冲突点 | 规避约定 |
|---|---|---|
| `ss-csv/src/main/resources/i18n/zh-cn.properties` | 同文件追加行易撞 | 键名空间即 `weapon.<id>.*` / `desc.<id>.*`，天然隔离；每组武器在自己分支内把该武器的键**集中插在文件末尾**，不插中间；最终合并时由收口人按 `weapon.` / `desc.` 分组、组内按 id 字典序重排。禁止同分支改动其他武器的键。 |

## 4. 共享工具清单

### 4.1 战斗随机数

已核实入口：`Misc.random`（public static `java.util.Random`）与 `Misc.getRandom(long seed, int numCalls)`。

- 战斗状态不参与存档序列化，「回档重掷」的真实风险是**同一场战斗内同一事件的随机结果在回放/重置时不一致**（如电驱不稳定装药在重开同一战斗时分布不同属可接受，但同一帧多次调用必须不重掷）。
- 统一口径：
  1. 每武器实例一个确定性序列：seed 派生自 `ship.id.hashCode() * 31 + slot.id.hashCode()`（战斗内稳定），调用序用 `weapon.customData` 不可得 → 用 BuffHost 的 Weapon 级状态位记 `callIndex`，取随机用 `Misc.getRandom(seed, callIndex++)`。
  2. 一次性纯视觉随机（粒子散布等不影响结算的）直接用 `Misc.random` / `MathUtils.getRandomNumberInRange`（现有渲染代码惯例）。
  3. 结算随机（装药倍率、EMP 触发概率）必须走 (1)；禁止同帧对同一事件二次取值。
- 落文件：`src/main/kotlin/cn/kasuminova/astd/impl/combat/CombatRandom.kt`（object，`nextFloatIn(seed, callIndex, range)` 一个入口，不做薄适配层族）。
