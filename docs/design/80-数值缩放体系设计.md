# 数值缩放体系设计案（P1 地基）

> 状态：设计案 v1.1（2026-07-27）。难度双轨制已登记为决策 D13；叙事档位定稿套 A（迟暮/砺刃/远征/破晓）；映射方式改为逐项登记、默认分段线性（防高档超线性收益）。
> 全局规则：下限克制、上限放开、玩家自由不受惩罚、文案禁忌见 90-roadmap.md §2。

## 1. 总纲：难度双轨制

难度体系拆成两条互不干涉的轨道：

| 轨道 | 名称 | 可见性 | 作用面 |
|---|---|---|---|
| 轨一 | **固有缩放系数** $k_s$ | 玩家在 LunaLib 设置界面自选 | 机制数值（船插 / 舰船系统 / 武器 / 词缀内部数值），仅作用于**敌方单位** |
| 轨二 | **进程动态系数** $k_p$ | 玩家不可见（模组内部） | 赏金舰队的**生成表**：舰队规模预算、旗舰出场阈值、词缀池数量与品质 |

设计动机：
- 轨一回答"这个模组应该有多难"——由玩家根据自己的模组组合与口味决定，一次设置全局生效。
- 轨二回答"这个玩家现在有多强"——由模组根据玩家舰队组成、军官、技能等数据自动评估，让赏金内容始终有压迫感。
- 两轨分离的硬约束：**轨二绝不触碰机制数值**。玩家堆强度不会被"敌人数值跟着涨"惩罚（自由规则）；压迫感通过规模与词缀组合的变化提供。

## 2. 轨一：固有缩放系数（LunaLib 玩家档）

### 2.1 档位

预设 4 档 + 自定义微调：

| 档 | 系数 | 叙事名 | 语义承诺 |
|---|---|---|---|
| Ⅰ | 1.0 | **迟暮** | 近原版压力。机制数值全部落在克制下限 |
| Ⅱ | 2.0 | **砺刃** | **默认。模组的标准设计难度**，机制数值落在设计基准 |
| Ⅲ | 3.0 | **远征** | 进阶压迫。数值进入基准与极限之间的前 1/3 |
| Ⅳ | 5.0 | **破晓** | 极限演出。为极端模组组合与自我挑战设计，数值落在放开上限 |

自定义：LunaLib 滑条 1.0~5.0（步进 0.1），供模组组合玩家精细对齐；预设档通过快捷按钮写入滑条。

档位定 4 档的理由：
- 2.0→5.0 跨 2.5 倍，没有中间档会在"默认嫌弱、极端嫌疯"之间断档，3.0 是资深玩家的合理落点。
- 每档必须有互斥的设计承诺；超过 4 档会稀释调校价值——每多一档，ARC/LENS 两线的平衡实测成本乘一倍。
- 滑条吸收长尾需求，预设档保持"给我一个说得过去的答案"的简洁性。

### 2.2 数值落地：三锚点声明 + 逐项映射

每个受缩放的机制数值按**三锚点写法**声明（对应"下限克制、上限放开"）：

```
v1 = 克制下限   // k_s = 1.0 时的值
v2 = 设计基准   // k_s = 2.0 时的值（平衡实测以这一档为准）
v5 = 放开上限   // k_s = 5.0 时的值
```

从 $k_s$ 到最终值的映射**逐项决定，默认分段线性**：

```
默认映射（分段线性）：
k_s ∈ [1, 2]：v = lerp(v1, v2, k_s - 1)
k_s ∈ [2, 5]：v = lerp(v2, v5, (k_s - 2) / 3)
```

- **线性不是铁律**：某些数值直接线性缩放会在高档位产生超线性收益（叠乘类属性、冷却转频率、概率转期望、AoE 范围转面积），导致特定武器或船插在 3.0/5.0 档过度膨胀。细化设计每一项数值时，设计者在该项登记处指定映射方式（线性 / 指数衰减 / 倒数 / 软上限 / 相对难度数值等），并写明选用理由。
- **过程量对玩家不可见**：$k_s$、锚点、映射函数全部是内部实现细节；玩家在 tip 文本与界面看到的只有应用后的最终数值。叙事档位（迟暮/砺刃/远征/破晓）是玩家侧唯一的难度表达，降低理解成本。
- 概率类数值同样走三锚点，但 v5 不得超过语义上限（如概率封顶 1.0、触发间隔封底下限）。
- 存量改造时，若某机制只有单值，先按 v2 登记现值，再补 v1/v5 两锚点。

### 2.3 作用面

- 敌方单位的船插数值、舰船系统数值、武器数值、词缀内部数值（伤害/概率/上限/持续）。
- **仅敌方**。玩家侧使用同一机制时固定取 v2（设计基准），避免玩家被自己的难度设置惩罚或奖励。
- 叙事文案中提及具体数值的条目（tip 文本），按 $k_s$ 动态替换占位符。

## 3. 轨二：进程动态系数（内部）

### 3.1 玩家战力评估

赏金生成时对玩家做战力快照 $S$：

```
S = Σ舰船(部署点 × 品级系数 q) + Σ军官(等级 × 3) + 玩家战斗技能数 × 4

q：基础 1.0
   每个 s-mod      +0.08
   每个 d-mod      -0.06
   相位/自动化舰    +0.10
   民用/后勤舰      ×0.5
   q 封顶 [0.5, 1.5]
```

数值选型原则：
- **可解释优先**：每个权重必须能写一行注释说清来由。FP 比值为骨架（沿用现有 DifficultyModel 思路），军官/技能/品级为修正项，单项影响控制在 ±30% 以内。
- 只统计主战成员：货舱里的船、封存军官不计入。

### 3.2 系数计算与压缩

```
S_ref = 该赏金威胁档位的基准战力（tier 基准 FP × 品质基准 1.0）
p_raw = S / S_ref
p     = sqrt(p_raw)，封顶 [0.85, 2.2]   // 边际递减压缩，防堆料惩罚
k_p   = (p - 0.85) / 1.35，归一化到 [0, 1]
```

- **边际递减**：堆到 4 倍战力的玩家面对的是 2 倍规模而非 4 倍——自由堆强度是玩家的正当玩法，压迫感靠词缀组合质量补，不靠线性放大的数量海。
- **迟滞**：$S$ 在赏金生成时快照，同一赏金生命周期内不变；连续生成取指数滑动平均（α=0.3），避免买卖船造成的规模抖动。
- 保留现有硬顶：威胁档难度倍率（T1~T5：1.0/1.25/1.65/2.25/3.0）× 进程系数 $p$，总倍率封顶 15 倍（沿用现有 DifficultyModel 上限）。

### 3.3 作用面

- **舰队规模预算**：budget = tier_base × p（沿用现有 FleetComposer 链路，playerMult 由纯 FP 比值换成 §3.1 的品质修正模型）。
- **旗舰出场阈值**：$k_p$ ≥ 0.6 的赏金允许生成旗舰级目标；$k_p$ ≥ 0.85 允许双旗舰编队。
- **词缀池**：沿用现有 `AffixRegistry.pickAffixes` 公式骨架（maxCount / tierCap / targetCount），输入 k 换为 $k_p$。池内词缀的**内部数值**仍由轨一 $k_s$ 决定（见 §4 矩阵）。
- 玩家侧可见性：赏金板显示威胁评估（现有星级），玩家自主决定接不接——难度变化可感知但评估过程不可见。LunaLib 调试页（仅 dev 开关）显示 $S$ / $p$ / $k_p$ 的计算分解，供实测核对。

## 4. 两轨交互矩阵

| 内容 | 轨一 $k_s$（固有） | 轨二 $k_p$（进程） |
|---|---|---|
| 船插 / 系统 / 武器机制数值 | ✔（敌方） | — |
| 词缀内部数值 | ✔（敌方） | — |
| 词缀池数量与品质 | — | ✔ |
| 赏金舰队规模 / 旗舰阈值 | — | ✔ |
| 玩家侧任何数值 | — | — |

**存量接错的挂点**：`BountyScalingHullMod` 目前用动态 k 缩放船体/装甲/幅能/航速——属机制数值，P1 改造为读取轨一 $k_s$；动态 k 仅保留在生成表链路。

## 5. 存量收编与落地步骤

1. **地基代码**：
   - 新增轨一来源：LunaLib 设置项读取 + 全局 `DifficultyTuning`（$k_s$ 单例，含三锚点插值工具函数）。
   - 轨二改造：`DifficultyModel.playerMultFromFleetAndBaseline` 升级为 §3.1 品质修正模型 + sqrt 压缩。
   - `BountyScalingHullMod` 切换到轨一；`AffixUtil.getK` 语义明确化为"生成表 k"，机制数值一律从 `DifficultyTuning` 取。
2. **存量船插/系统逐个改造**：全部"概率/上限/浮动"数值改三锚点写法，逐个登记改造清单（断熵弧刃虚粒子上限 6~18 为首个样板）。
3. **叙事文案数值占位**：tip 文本中的硬编码数值改占位符替换。
4. **验证**：
   - 单元测试：三锚点插值端点与分段点；$S$ 评估的边界（空舰队 / 纯后勤舰队 / 全 s-mod 旗舰队）。
   - 实机：同一敌舰在 $k_s$=1.0 / 2.0 / 5.0 下机制表现差异可观测；$k_p$ 分解页与实估一致。

## 7. 功能实现计划（Api / Impl 分离）

> 包结构沿用既有约定（`api/render` ↔ `impl/render`）：接口层进 `api/difficulty`，实现层进 `impl/difficulty`；轨二实现贴近赏金域，放 `campaign/bounty`。
> 命名约定：`Xxx`（接口）/ `XxxImpl`（实现）；接口注释包含类简介、动机、成员作用。

### 7.0 依赖接入（前置）

- `gradle.properties` 的 `mod.dependencies` 追加 `lunalib:LunaLib`（游戏 mods 目录已有 `Lunalib`，jar 会被 `DependencyConfig.starsector()` 自动扫入 compileOnly）。
- 编译验证：`compileKotlin` classpath 含 `LunaLib.jar`。

### 7.1 接口层 `api/difficulty`（4 个文件）

| 接口 | 职责 |
|---|---|
| `DifficultyTuning` | **轨一读取面**。`val fixedScale: Float`（当前 $k_s$，1.0~5.0）；`fun value(entry: ScalingEntry): Float`（按 entry 的映射取最终值）。敌方机制数值统一由此派生。 |
| `ScalingEntry` | **单个机制数值的三锚点声明**（data class）：`v1 / v2 / v5 + map: ScalingMap = ScalingMap.LINEAR`。使用处就地声明，即"逐项登记"的落点。 |
| `ScalingMap` | **$k_s$ → 最终值的映射策略**（fun interface）：`fun value(k, v1, v2, v5): Float`。内建 `LINEAR`（分段线性，两段在 k=2 处连续）；高档超线性收益项由使用处以 lambda 或新实现类登记保守映射，并写明理由。 |
| `FleetStrengthAssessment` | **轨二读取面**：`fun assess(): StrengthSnapshot`。`StrengthSnapshot` 含 `score(S) / reference(S_ref) / p / k(k_p) / breakdown`（逐项贡献分解，供调试输出与测试断言）。 |

调用侧约定：逻辑层字段一律声明为接口类型（如 `private val tuning: DifficultyTuning = DifficultyTuningImpl`），禁止把 Impl 类型扩散进方法签名。

### 7.2 实现层 `impl/difficulty`

| 类 | 职责 |
|---|---|
| `DifficultyTuningImpl` | `object`，实现 `DifficultyTuning`。内部持有当前 $k_s$（默认砺刃 2.0）；提供 `installScaleForTests(scale: Float?)` 供单元测试注入（不用反射）。类初始化不触碰 LunaSettings——单测环境无 LunaLib。 |
| `DifficultySettingsKeys` | LunaLib field id 常量 + 档位显示名 ↔ 系数映射（单一持有处）。读取按显示字符串精确匹配，未命中回退 2.0 并打 warn 日志。 |
| `DifficultySettingsRegistrar` | LunaLib 设置注册：`addRadio`（迟暮/砺刃/远征/破晓/自定义，默认砺刃）+ `addDouble`（自定义系数 1.0~5.0 步进 0.1，仅"自定义"档生效）+ 档位描述文本；`LunaSettingsListener.settingsChanged` 时重读并刷新 `DifficultyTuningImpl`。在 `AsteriaDirectoratePlugin.onApplicationLoad` 挂接。 |

### 7.3 轨二实现（`campaign/bounty` 域）

- `FleetStrengthAssessmentImpl`：按 §3.1 公式评估（舰船部署点×品级 q、军官等级×3、战斗技能×4；只统计主战成员）；`S_ref` 取赏金 tier 基准 FP；`p = sqrt(S/S_ref)` 封顶 [0.85, 2.2]；EMA 平滑（α=0.3）；生成时快照。
- `DifficultyModel` 升级：`playerMultFromFleetAndBaseline` 改走 `FleetStrengthAssessment`；tier 倍率（1.0/1.25/1.65/2.25/3.0）与总倍率 15 倍硬顶保留不动。
- `FleetComposer` 接线不变，词缀池 `pickAffixes` 的 k 输入即 $k_p$（语义不变，来源升级）。

### 7.4 存量接轨

- `BountyScalingHullMod`：弃用动态 k，改读 `DifficultyTuning`。每项属性改三锚点（例：船体加成 v1=1.00 / v2=1.05 / v5=1.20，现值登记为 v2，v5 为放开上限）。
- `AffixUtil.getK`：注释明确"生成表专用 k_p，机制数值禁止从此取"。
- **样板改造**：断熵弧刃虚粒子上限（6~18）改 `ScalingEntry` 三锚点写法，作为后续逐项改造的参照范例。

### 7.5 i18n 与文案

- 新增 `contents/data/strings/settings_strings.json`（注册进 `I18n.kt` 文件清单）：设置页标题、5 个档位显示名、4 段档位描述（§6 定稿文案）、自定义滑条说明。
- 过程量（$k_s$、锚点、映射）不进任何玩家可见文本；tip 数值占位替换属后续步骤，不在本轮。

### 7.6 可观测性

- 赏金生成时输出 INFO 日志：`S / S_ref / p / k_p` 逐项分解（含品级修正明细），实机核对用 `starsector.log` 即可，不做额外 UI。
- $k_s$ 变更（设置保存）时输出一条 INFO 日志记录新档位。

### 7.7 测试与收口

- 单元测试：
  - `ScalingMap.LINEAR`：端点（k=1/2/5 命中 v1/v2/v5）、分段中点、段间接合连续；
  - `DifficultyTuningImpl`：注入系数后 `value(entry)` 全链路；显示名未命中回退 2.0 + 日志；
  - `FleetStrengthAssessmentImpl`：边界（空舰队 / 纯后勤舰队 / 全 s-mod 旗舰队）、sqrt 压缩单调性、封顶生效；
  - `BountyScalingHullMod`：在注入 $k_s$=1.0 / 5.0 下调用验证加成取对应锚点值（完整逻辑验证，非源码 contain）。
- 全量 `./gradlew test --rerun-tasks` 通过后部署烟测（部署前记得 `rm -rf build/generated/ss-csv` + `cleanDeploy` 的旧坑）；automation 到达终态即关游戏。
- 台账：P1 地基条目勾选、提交号入日志。
