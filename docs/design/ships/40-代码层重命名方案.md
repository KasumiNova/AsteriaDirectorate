## 2. ID 策略：三方案对比（核心裁定项）

| | A. 英译跟随 | B. 代号 ID 全量迁移 | C+. 遗留 ID 冻结 + 显示名全量 |
|---|---|---|---|
| 做法 | ID 改为新名英译（astd_starfall 等） | ID 改为代号（astd_xc_001 等），§5 有完整实施细则 | ID 一律不动，只改显示名层 |
| 抗改名 churn | ❌ 三天内已改名 3 次（折光→鸢尾→决明），英译 ID 必然再碎 | ✅ 代号是 in-universe 正式标识（D26 俗称口径：总局只编目不命名），舰名再改 ID 不动 | ✅ ID 退化为纯内部契约，与显示名解耦 |
| 改动面 | 全量（同 B） | 全量：55 数据文件 + 28 贴图改名 + ~50 代码点 + i18n 键全改 | 仅显示名层（§3 L0/L1），不动 ID |
| 存档兼容 | 旧档作废 | 旧档作废（hull id 变化无法迁移，需开新档） | ✅ 零风险（显示名不入档） |
| 调试可读性 | ✅ 好 | ⚠️ 日志里 astd_xc_101 需查对照表（缓解：代号自带线码/档位语义，00-common §2.4 加 ID 列） | ✅ 保持现状 |
| 英文起名问题 | ❌ 又是一场命名工程 | ✅ 彻底消灭（不再需要英文类名） | ⚠️ 遗留英文名仍在数据里 |
| 前置依赖 | 英译名定案 | 代号格式随本方案启用即定案（§5.1 分配表） | 无 |

**两个可执行方案并列待拍板：**

- **C+（保守）**：只动显示名层，零风险、工作量小；代价是 ID 永久与新名脱钩（`astd_gravitational_lens` = 决明级），靠 00-common §2.4 对照表维持映射。
- **B（彻底）**：ID 全量迁移到代号制（§5 实施细则已备）。一次性成本换三个长期收益：① **改名免疫**——发布前舰名已 churn 三轮，代号 ID 对此天然免疫；② **英文起名问题彻底消失**；③ 与俗称口径（D26：总局只编目不命名，两字名是使用者俗称）完全自洽，数据层 ID 即 in-universe 正式标识。时机价值：**mod 未发布，"旧档作废"的成本现在最低**，发布后 ID 被存档锁死就再无此窗口。
- 方案 A 否决：英译 ID 在三轮改名面前必然再碎。

1. **禁止全局盲替换「星坠」**：新名「星坠」与既有 `world.system.starfall.name=星坠`、`菀星设计局-星坠`、`星坠理事会`（tech 列）同字——替换方向是旧名→新名，不涉及把「星坠」换成别的；但反向核查 diff 时注意不要误改势力/星系上下文。
2. 禁止手改 `contents/` 下 ss-csv 生成物（五张 CSV + `.system` + `.proj`）；改 entry/i18n 后生成。
